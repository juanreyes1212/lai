The dashboard upload flow on Tails & Scales does three things to
every image *before* it sends a single byte to Supabase Storage:
compress, measure, blur-encode. The first cuts storage costs, the
second eliminates layout shift, the third makes the gallery feel
instant. All three run in the browser, in parallel, with no native
dependencies.

## Step 1 — Compression

`browser-image-compression` resizes anything larger than 2400px on
the long edge and caps the file at 3 MB. Diego shoots in 24-megapixel
RAW; the web-friendly export from Lightroom is usually 8–12 MB. The
compression pass takes those down to 1–2 MB without visible quality
loss at the resolutions a gallery actually displays at.

```ts
import imageCompression from 'browser-image-compression'

const compressed = await imageCompression(file, {
  maxSizeMB: 3,
  maxWidthOrHeight: 2400,
  useWebWorker: true,
})
```

`useWebWorker: true` is what keeps the upload UI responsive while
big files are being resized. Without it, ten queued files freeze
the main thread for ten seconds.

## Step 2 — Dimensions via canvas

Storing `width` and `height` next to the image URL is what
eliminates layout shift. The gallery's masonry grid can compute the
aspect ratio from the row data and reserve the correct space
*before* the image is fetched.

```ts
const dims = await new Promise<{ width: number; height: number }>((resolve) => {
  const img = new Image()
  img.onload = () => resolve({ width: img.naturalWidth, height: img.naturalHeight })
  img.src = URL.createObjectURL(compressed)
})
```

The temptation is to read EXIF for this. EXIF lies — rotated phone
photos report their pre-rotation dimensions, and you spend a week
chasing landscape thumbnails that render portrait. Loading the
compressed blob into an `<img>` and reading `naturalWidth` gives
you the dimensions the browser will actually paint, which is the
number the layout engine needs.

## Step 3 — Blur placeholder

A 20×20 JPEG, base64-encoded, stored on the row. That string is
under 1 KB. The gallery renders it as a `background-image` on the
container that wraps the real `<img>`, scaled up with `filter: blur(20px)`.
When the real image loads, it fades in over the blur.

```ts
async function makeBlurPlaceholder(blob: Blob): Promise<string> {
  const img = await loadImage(blob)
  const canvas = new OffscreenCanvas(20, 20)
  const ctx = canvas.getContext('2d')!
  ctx.drawImage(img, 0, 0, 20, 20)
  const tiny = await canvas.convertToBlob({ type: 'image/jpeg', quality: 0.5 })
  return await blobToDataUrl(tiny)
}
```

`OffscreenCanvas` runs off the main thread when it's transferred to
a worker, which matters when the upload queue is processing three
files at once. The output is roughly 600 bytes — small enough to
ship inside the initial JSON response from the gallery query, so
the placeholder paints on the first render, before any image
request fires.

## What this looks like on the receiving end

The gallery row in the database stores all three artifacts:

```sql
CREATE TABLE gallery_images (
  id uuid PRIMARY KEY,
  storage_path text NOT NULL,
  width integer NOT NULL,
  height integer NOT NULL,
  blur_data_url text NOT NULL,
  ...
);
```

The masonry component reads the row, reserves a slot at the right
aspect ratio, paints the blur, and *then* requests the real image.
There is no period during page load where the layout reflows or
where a slot is empty. The blur is on screen for somewhere between
40 ms (cached) and 800 ms (cold), depending on connection — but
either way, the layout is stable from frame one.

## The lesson I keep relearning

Image performance work is almost entirely *what you do before the
image is requested*. The browser's job is to paint pixels; if you
give it everything it needs to paint a correct layout without the
file, the file becomes a progressive enhancement instead of a
blocking dependency. Three small browser-side jobs replace what
would otherwise be an entire image-CDN integration.
